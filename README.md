# mingtu — 肠道菌群健康顾问

一个面向中国普通用户的肠道微生态科普 RAG 智能体。它做的是「把证据按可信度分层讲清楚」和「判断什么情况该去看医生」，不做诊断。

这份文档写给接手这套代码的工程团队。读完你应该知道：每个模块负责什么、为什么这么切分、哪些地方是刻意不优雅的，以及现在还差什么。部署和运维看 [DEPLOY.md](DEPLOY.md)。

---

## 1. 这个智能体是什么

输入是一句中文提问，输出是一段中文回答加一份来源清单。中间做四件事：

1. **确定性安全筛查**：先用正则扫消化道报警症状。命中且是第一人称叙述，直接走固定的就医话术，整条链路不经过任何模型。
2. **混合检索**：BM25 + 向量双路召回，RRF 融合，按证据等级/人群/法规属性加权，配额保证特定类别不被挤掉。
3. **作答**：Claude 基于本轮检索到的编号资料写答案，每条实质结论必须标注来源编号。
4. **出口校验**：校验引用编号真实存在，校验文本不含《广告法》《食品安全法》禁止的健康宣称。不合格就带纠正指令重写，重写仍不过就拒答。

定位边界写死在系统提示词里：不诊断疾病、不解读检验报告、不推荐处方药、不评估病情严重程度、不推荐具体品牌。

## 4. 为什么这么设计

### 4.1 为什么急症判定不交给模型

这是整个系统里唯一一处「模型不参与」的决策，理由有三条。

**第一，失败模式不对称。** 报警症状漏判的代价是漏诊消化道肿瘤；误判的代价是多说一句「建议去消化科看看」。这两个代价差好几个数量级，所以 `RED_FLAGS` 是刻意过度包含的——它匹配的是普通人真实的说法（「大便有血」「瘦了好几斤」「厕纸上有血」），不是教科书写法（「便血」「不明原因体重下降」）。宁可多拦，不可漏拦。

**第二，模型的判断不可复现也不可审计。** 同一句「我最近大便有血」，模型可能这次判 emergency 下次判 caution，取决于上下文长度、温度、版本。正则不会。上线一个医疗相关产品，你必须能对监管或对法务说清楚「什么输入一定会触发就医提示」，这句话只有确定性代码能兑现。

**第三，模型可以被绕过。** 提示词注入、长上下文稀释、越狱模板，都可能让模型不执行「先给就医建议」这条指令。`screen_input` 跑在模型之前，`escalation_message` 是硬编码文本直接 `return`，中间没有任何模型输出参与，所以注入攻击、检索失败、API 超时、模型拒答——都不能让这条路径失效。

具体实现是**只升不降的合并**（`classify.py:78-81`）：

```python
order = {"normal": 0, "caution": 1, "emergency": 2}
if order[floor] > order[result["risk"]]:
    result["risk"] = floor
```

模型可以把 normal 升到 caution，可以把 caution 升到 emergency，但**不能**把正则定的 emergency 降回去。模型在这里只有加保险的权力，没有拆保险的权力。

这条设计的代价是误报。「便血是什么原因造成的」这种纯科普提问，如果句子里出现「最近」「一直」这类第一人称信号词，也会被 `mentions_self` 判成自述而升级。我们接受这个代价，没有做降级通道。

### 4.2 为什么是混合检索而不是纯向量

因为这个语料里价值最高的事实，恰好是向量最不擅长表示的那一类。

**菌株号。** `DSM 17938` 和 `DSM 9843` 在向量空间里几乎重合——同样的前缀、同样的数字形态、同样的语境。但它们是两个不同的菌种（*Lactobacillus reuteri* 和 *Lactiplantibacillus plantarum* 299v），适应症不同、证据强度不同。纯向量检索会把它们混在一起，答案里就会出现「张冠李戴的菌株」，这在本产品里属于严重缺陷。BM25 是精确词项匹配，能把它们分开。剂量（`10^10 CFU`）、法规文号、国标编号，同理。

**反过来，纯 BM25 也不够。** 用户说「吃了益生菌还是胀气」，语料里对应的是「产气与腹胀耐受阈值」「低聚果糖 FOS 剂量区间」。两者词面几乎不重叠，BM25 召不回来，向量可以。

所以两路都要。融合用 **RRF（倒数排名融合）而不是分数加权**：BM25 分数和余弦相似度不在同一个量纲上，要混合就得先归一化，而归一化的参数会随语料变化——这是个永远调不完的活。RRF 只用两边的排名序，不用分数，天然免疫量纲问题。

```
score(d) = Σ  1 / (60 + rank_i(d))          再 ×100 便于和元数据加权同量级
```

**元数据加权是刻意做得很轻的**（A 级 +0.30，法规 +0.45，人群匹配 +0.35）。这些只微调排序，不覆盖相关性。一段完全对题的 D 级证据仍然应该排在完全不对题的 A 级证据前面——因为模型需要看到它，才能对用户说「这个只在动物实验里看到过」。如果直接过滤掉低等级证据，模型就无从判断「证据不足」，只能沉默或者编。

**配额是加权解决不了的问题的补丁**（`_quota_select`）。加权只能在已经召回的结果里重排；对于法规类提问，如果法规段落的词面重合度太低，它根本进不了候选池，再高的权重也没用。所以法规问题预留 3 个席位、特定人群预留 2 个席位，硬保证这类资料在场。

**近重复抑制**是因为切块有 90 字重叠，同一节的相邻块内容高度相似，不抑制的话一节内容能占满 rerank 的全部 8 个名额，把其他章节完全挤掉。当前的抑制键是 `(source, heading)`——同一文件同一标题只保留一块。

## 5. 证据分级体系

分级贯穿三层：研究阶段生成、切块阶段抽取、作答阶段传达。

| 等级 | 定义 | 面向用户的说法 |
|---|---|---|
| A | 人体 RCT 的荟萃分析 / 系统综述 | 「这个是有比较扎实的人体研究支持的」 |
| B | 单个人体随机对照试验 | 「有一项人体试验支持，但还需要更多验证」 |
| C | 队列研究 / 观察性研究 | 「目前只看到相关性，因果关系还不清楚」 |
| D | 动物实验或体外实验 | 「这个目前只在动物或细胞实验里看到，人身上还没验证」 |
| E | 专家意见或机制推测 | 「这个更多是理论推测，还没有直接证据」 |

**硬性规则**（写在 `prompt.py` 的 `EVIDENCE_RULES` 里）：只有 D 或 E 级证据的说法，必须明确说「证据还不够，不能当结论」，不允许用肯定语气陈述。涉及菌株必须写到菌株号，不能只说「乳酸菌」。涉及剂量必须给单位、疗程和适用人群。

除了 A-E 分级，每块还带一个正交的 `authority` 字段（`meta-analysis` > `guideline` > `rct` > `cohort` > `animal` > `opinion`），由 `chunker._AUTHORITY` 按关键词抽取，最先命中的胜出。这个字段只参与检索加权，不直接展示给用户。

**当前索引的实际分布（443 块）：**

| 维度 | 分布 |
|---|---|
| 证据等级 | 未标注 272、A 62、B 35、E 30、C 28、D 16 |
| 权威性 | meta-analysis 173、unspecified 97、guideline 78、rct 69、opinion 11、cohort 9、animal 6 |
| 法规块 | 68 |
| 人群 | 通用 249、成人 100、婴幼儿 81、儿童 65、免疫抑制 17、孕产妇 11、老年 9 |
| 带 URL 引用 | 21 |
| 来源分布 | 04-limits 98、05-systemic 97、03-china-reg 90、01-strains 81、02-diet 77 |

**272/443 块没有证据等级**，这是当前最大的数据质量缺口——见第 9 节。

## 6. 安全与合规边界

### 闸门一：输入报警症状（`RED_FLAGS`，15 组正则）

便血、黑便、呕血、体重下降、吞咽困难、持续呕吐、贫血、腹部包块、夜间症状、黄疸、发热伴腹痛、剧烈腹痛、脱水、消化道疾病家族史、排便习惯改变。

命中后行为分两种：

- **判定为 emergency**（命中 + 第一人称）：走 `ESCALATION_TEMPLATE` 固定话术，直接返回。这段文本是全系统唯一一段模型不参与生成的用户可见文本。
- **判定为 caution**（命中但非自述）：注入 `REFERRAL_INSTRUCTION`，要求模型区分「用户在描述自己症状」和「用户在问这个症状的科普」，前者把就医建议放最前面，后者正常科普但结尾提示。

### 闸门二：输出违规宣称（`BANNED_CLAIMS`，7 组正则）

对应《广告法》第十七条和《食品安全法》第七十三条：

| 模式 | 拦什么 |
|---|---|
| 治疗\|治愈\|根治\|痊愈\|药到病除 | 疾病治疗功能宣称 |
| 预防…病/癌/症/炎 | 疾病预防功能宣称（「预防接种」已排除） |
| 替代\|代替…药物/治疗/就医 | 宣称可替代医疗 |
| 无\|没有\|零…副作用 | 无副作用宣称 |
| 100%\|百分之百\|绝对有效\|保证治好 | 绝对化用语 |
| 特效\|神效\|秘方\|奇效 | 夸大功效 |
| 最好/最强的益生菌/产品/菌株 | 绝对化最高级 |

**逐句扫描，否定语境豁免。** 「益生菌不能治疗肠炎」不算违规，「益生菌可以治疗肠炎」算。豁免靠 `_NEGATED` 正则匹配句内的否定词（不能、不得、禁止、违法、并非、没有证据……）。

命中是**失败而不是警告**：调用方带纠正指令重写，最多两轮，两轮不过就拒答。想让某个回答通过而去放宽这张表，是错误的修法——那等于把所有后续回答的合规底线一起降了。

### 就医边界与特殊人群

系统提示词强制要求：免疫抑制、危重症、中心静脉置管、短肠综合征、早产儿、化疗或器官移植后，使用益生菌前必须先咨询医生，且要主动提醒。孕妇、哺乳期、婴幼儿、正在服药（尤其抗生素、免疫抑制剂）的用户，给建议时必须单独提示与医生确认。

### 每个 LLM 阶段的兜底

| 阶段 | 模型不可用时的行为 |
|---|---|
| 分流 | `infer_filters` 提供确定性过滤条件，risk 取正则给的 floor，子查询退化为原问题 |
| 重排 | 回退到混合检索原序（已加权、已配额） |
| 作答 | 返回明确的「未配置 key」提示，不伪装成正常回答 |
| 实时检索 | 返回 `[]`，主链路继续 |

安全层完全不依赖模型，所以 API 全挂时急症判定照常工作。这一点已验证：在没有任何 `ANTHROPIC_API_KEY` 的环境下，输入「我最近大便有血，还瘦了五斤」仍然正确返回 emergency 和完整就医话术。

## 9. 已知限制与未做的事

按严重程度排序。前四条会直接影响线上表现，上线前必须处理或至少明确接受。

### 9.1 上线阻塞项

**（1）`ANTHROPIC_API_KEY` 当前在任何位置都不存在。** `llm.py` 只从环境变量、`~/Desktop/dev/curio/.env`、`~/Desktop/dev/Curio-Automation/.env` 三处找，这两个 `.env` 里都没有 Anthropic 的 key。当前状态下所有回答都是「【未配置 ANTHROPIC_API_KEY，无法生成回答】」，检索和安全层正常但作答层完全不工作。这是第一个必须解决的问题。

**（2）重写循环里的 system 消息位置不合法。** `core.py:168` 在一条 assistant 消息之后追加 `{"role": "system", ...}`：

```python
messages.append({"role": "assistant", "content": answer})
messages.append({"role": "system", "content": "\n".join(fixes)})
```

会话内 system 消息（claude-opus-5 支持，无需 beta header）要求必须跟在一条 `user` 消息之后，或跟在以服务端工具调用结尾的 assistant 消息之后。这里跟的是纯文本 assistant 消息，按接口约束会被拒绝，异常被 `_generate` 的 `except Exception` 吞掉并返回 `None`，用户看到的是「抱歉，这一轮没能生成回答」。

**后果是引用校验和合规校验的重写通道实际上不生效**——首轮不合格就直接变成一句道歉。第一处 system 消息（`core.py:136`，紧跟 user 消息且位于末尾）位置是合法的，只有重写循环这一处有问题。

修法二选一：把纠正指令改成 `{"role": "user", ...}`，或者在 assistant 之后先补一条 user 消息再放 system。改完必须用真 key 跑一次带违规词的回答，确认重写循环真的转起来了（当前没有 key，这条判断依据的是接口约束而非实际返回）。

**（3）实时检索结果拿不到重排席位。** `core.gather` 里，live 段落的 `_score` 被硬编码为 `0.0`，而 pool 在切片前按分数降序排：

```python
pool.sort(key=lambda c: c["_score"], reverse=True)
passages = rerank(query, pool[:24], top_n=TOP_N)
```

实测单个子查询的本地检索就返回满 24 条（分数区间约 1.5–3.1），所以 `pool[:24]` 会被本地结果占满，实时检索的段落在进入重排器之前就被切掉了。只有本地召回不足 24 条时实时结果才有机会出现。

这意味着 `live.py` 这条链路目前近似空转：会花掉 Perplexity 的调用和 60 秒超时预算，但结果进不了答案。修法是给 live 段落一个能进候选池的初始分（比如本地分数中位数），或者在切片时给 live 保留固定席位。

**（4）语料里的 `[N]` 标记与本系统的引用编号冲突。** `research/*.md` 是 Perplexity 生成的，正文里带着它自己的引用标记 `[1][2][3]`。这些标记原样进了索引：**443 块里有 365 块含 `[N]` 标记，其中 217 块含 1–8 范围内的编号**，正好和本轮资料的编号区间（1..8）重叠。

风险有两层：模型可能照抄段落里的 `[13]`，被 `validate_citations` 判成编造编号（触发一轮无谓重写）；更糟的是照抄 `[3]`，落在合法区间里，校验通过但指向完全不相干的来源，且无法被发现。

修法是在 `chunker.py` 里剥掉源文档自带的 `[N]` 标记，或者把本系统的引用格式改成不会撞车的形式（比如 `【S3】`）。改完需要重建索引。

### 9.2 数据质量

- **272/443 块没有证据等级**（占 61%）。这些块的 `GRADE_BOOST` 为 0，且模型拿到它们时看到的标签是「未标注等级」，没法向用户传达可信度。原因是 `chunker._GRADE` 只认三种写法（`证据等级：A`、`（A级）`、`A级证据`），而研究文档里大量结论用的是别的表述。
- **只有 21/443 块带 URL**。`_URL` 正则是逐块跑的，而 Perplexity 把参考文献集中放在文档末尾的「## 来源」一节，绝大多数正文块里没有链接。结果是 `sources` 清单里大部分条目没有可点验证的出处。
- **年份抽取有噪声**。`_YEAR` 会匹配文中任意 4 位年份并取最大值，包括文献列表里提到的年份，不一定是这段结论本身的年份。当前有 19 块的年份 ≥2026（部分是真实的 2026 年文献，部分是误抽）。
- **单一数据源**。全部 443 块来自同一批 Perplexity `sonar-deep-research` 输出，没有第二来源交叉校验，也没有人工审核记录。

### 9.3 工程缺口

- **没有网页端。** `web/` 是空目录。
- **没有 CLI 入口。** 没有 `cli.py`，`core.py` 也没有 `__main__` 块，只能用 `python -` 或 REPL 调用。
- **没有测试。** 安全层的正则、豁免逻辑、只升不降的合并规则，全都没有测试覆盖，改动没有回归保护。这几处是最该先补测试的地方。
- **没有依赖清单。** 没有 `pyproject.toml`、`requirements.txt` 或 lock 文件，依赖版本只存在于 `.venv` 里。
- **没有日志。** `_generate` 和 `call_json` 都是 `except Exception: return None`，认证失败、限流、超时、拒答在外部完全不可区分，线上排障基本靠猜。
- **索引一致性无校验。** `load_index` 不检查 `chunks.jsonl` 行数与 `vectors.npy` 行数是否一致。两者不一致时不报错，而是静默返回错位的检索结果。
- **不是 git 仓库。** 没有版本历史，改坏了没法回滚。

### 9.4 行为与模型层面

- **`max_tokens` 与默认开启的 thinking 相互挤占。** claude-opus-5 省略 `thinking` 参数时默认开启自适应思考，而 `max_tokens` 是思考加正文的总上限。当前分流用 1024、重排用 4096、作答用 8000。分流那 1024 尤其紧，一旦思考吃掉预算，JSON 输出会被截断，`json.loads` 失败，静默退回确定性兜底——功能不会崩，但分类器实际生效比例可能远低于预期，而且没有任何日志能看出来。上线后应该实测各阶段的 token 用量再调。
- **没有配置拒答回退（`fallbacks`）。** claude-opus-5 的安全分类器可能返回 `stop_reason: "refusal"`。代码检查了这个字段并返回 `None`，但没有配置服务端 fallback，一次拒答就等于一次失败。医疗健康类提问触发误判的概率不为零。
- **多轮对话的安全筛查只看当前轮。** `screen_input` 只扫本轮 `query`。用户在第一轮说「我最近大便有血」、第二轮只说「那我该吃什么益生菌」，第二轮不会命中报警症状，也不会重新升级。`answer()` 虽然接受 `history` 参数，但历史消息不参与安全筛查。
- **`mentions_self` 判据很粗。** 只是匹配「我/自己/本人/最近/这几天/一直/老是/总是」。「便血最近很多人在问」这类句子会被误判成自述并升级到 emergency。刻意偏向误报，但没有任何降级通道。
- **近重复抑制只看 `(source, heading)`。** 同一标题下的不同小节内容差异较大时会被误抑制，只保留第一块。
- **配额与 `top_n` 可能冲突。** 法规 3 席加人群 2 席共 5 席，`top_n` 为 8 时留给通用相关性的只有 3 席。极端提问下相关性最高的段落可能进不了最终列表。
- **索引重建是全量的。** 新增一份研究文档要重新向量化全部 443 块，没有增量更新。
- **没有速率限制、没有会话持久化、没有成本追踪。**

## 10. 关键设计约束（改动时按这些衡量）

改代码前先确认没有破坏这七条。它们是这个产品的底线，不是优化项。

1. 急症判定绝不能只依赖模型。`safety.screen_input` 是确定性的，分类器只能升级不能降级。
2. 每个 LLM 阶段都必须有确定性兜底。API 挂了安全层仍要工作。
3. 回答必须逐条标注来源编号，编造编号视为严重缺陷。
4. 资料不足时必须弃答，不能用不对题的内容凑答案。
5. 所有面向用户的文本必须是中文，且不能有 AI 腔（不要「希望对您有帮助」这类）。
6. 不得出现中国《广告法》《食品安全法》禁止的健康宣称。
7. 定位是科普与就医导航，不是诊断工具。

特别提醒第 6 条：**为了让某个回答通过而放宽 `BANNED_CLAIMS`，是错误的修法。** 问题出在生成端就在生成端修（改提示词、改重写指令），不要动闸门。闸门放宽一次，之后所有回答的合规底线都跟着降了。
